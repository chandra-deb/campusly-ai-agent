# Learning from implementation

For each decision keep one example the owner can reproduce, the alternative considered and what failed. Review the actual receipt, source or retry trace together before recording a lesson. Track owner understanding separately from passing tests.

For a later ML study, freeze model/version, tool contracts, held-out synthetic cases and scoring rules before comparing grounding, abstention, useful replies, action integrity, privacy, latency and cost. Preserve failures and limitations. Core owns the infrastructure experiments and Cloud report. This repository owns the living ML report draft and AI engineering blog drafts; cross-link sanitized evidence to the core report when relevant. A research claim needs evidence beyond a successful demo.

## Working loop

1. Before work: identify the user problem, alternatives, expected behavior and relevant report section; define hypotheses before formal measurement.
2. During work: record design choices, debugging, negative cases, reproducible commands and actual observations.
3. After each substantive task: update diagrams/ADR if needed, a technical blog draft and the relevant living course-report draft (or a documented N/A). Use `docs/reports/ML_REPORT_DRAFT.md` and `docs/blog-drafts/` as the starting paths for AI-owned drafts; create them when the first relevant task is authorized. Core owns its Cloud report; do not copy private source into this public repository.
4. Owner review: understand the implementation, verify the evidence, revise drafts and separately approve submissions/publication. A report or paper is the outcome of engineering, not the driver of arbitrary features. Protect course deadlines.

For each visible slice capture sanitized screenshots, the owner's manual scenario and actual feedback, including bugs and rejected designs. Link them to the milestone and revision. ADR 0002 is planning rationale for the first relevant report/blog, not a measured result.
