# Engineering rules

The owner approved the product direction and a standalone public repository. Each implementation milestone needs an approved design and explicit scope. Local acceptance is the owner's decision. Real-data processing, recurring jobs, external rollout, spending and publication require separate permission.

Core checks current tenant, membership, activity and action capability on every tool read and write. A draft, memory entry, prompt or service credential cannot confer a user's authority. Bind approval to the exact actor, action, target and payload. An edited draft needs fresh approval. Post shared replies as the bot and approved drafts as the human with an internal receipt.

Keep private inquiries outside shared AI delivery, retrieval, caches, prompts, logs and telemetry. Group conversations live in core. Store only necessary AI-owned state, isolate scopes and define deletion before persistence. Synthetic fixtures must work without importing private source or contacting a provider.

Start from an organizer's problem. Record a decision and a reproducible check as the work happens. Register hypotheses before formal measurement and retain adverse findings. This repository is intentionally public as a portfolio and product demonstration for prospective customers, supervisors and employers. Review ownership, licensing, privacy, dependencies, documentation and changes before every public commit; keep private core source, secrets, identifiable data and sensitive operational details out of public history. Owner approval is required for product rollout, external blog/paper publication and real-data processing.

## Product-first development and deployment

Deliver the smallest useful, secure AI prototype on a single host alongside core. Keep independently runnable service/worker boundaries and versioned interfaces so HTTP, workers and realtime delivery can later scale separately; no distributed deployment is required for the prototype. Owner local review, relevant tests and a separate rollout decision precede shipping. Scale-out is a later engineering phase, not a blocker for the local AI slice. Do not let research ambitions delay academic deadlines.

## Living evidence

Engineering decisions, debugging, diagrams, tests and actual results feed incremental technical blog and Cloud/ML report drafts as work happens. The work is driven by product needs and approved engineering objectives, not by a predetermined report or paper conclusion. Every substantive task updates the relevant drafts or records an explicit N/A reason. Formal experiments freeze hypotheses, controls and scoring before measurement; papers follow only if evidence warrants them. Track owner understanding and report review independently of engineering verification.

## Visible vertical slices and complete responses

Develop one small user-facing capability across UI, core and AI at a time. Each slice is locally usable, tested and reviewed by the owner before acceptance. Start president-only; add authorized reads, drafts and confirmed actions in separate increments. Personal memory precedes shared group AI in the planned order; group and organization intelligence follow in smaller slices. Return whole responses, not token streams. Show loading and error states; asynchronous jobs may return complete results later. Do not defer security, deletion or safe retry behavior needed by the current slice. Technology and implementation scope need separate approval.

## Real-model validation gate (owner decision, 2026-11-26)

For every AI phase, first implement the scoped UI/Core/AI functionality and pass focused deterministic tests, including failures and authorization. Keep the fake adapter for repeatable, credential-free regression. Then connect the actual LLM and native tool orchestration, and exercise **all** capabilities introduced in that phase against the owner's existing local Campusly development database, which contains only dummy data. Do not require a second synthetic database for manual testing; disposable fixtures remain useful for automated checks. A hosted adapter smoke or hardcoded-intent demo alone is not real-agent acceptance.

Record deterministic verification, live-model verification and owner acceptance independently. A phase cannot be called complete or advance to the next phase until relevant real-model and end-to-end checks pass and the owner accepts it. Record a blocked provider, failed tool call or untested capability as such; fix or obtain an explicit owner scope decision rather than silently skipping it. A–C have deterministic evidence but their real-model gate is open; complete R1–R4 before D1.

Use typed model tool calls where appropriate, bounded execution and validated arguments/results; reuse existing Core functions, not privileged direct database access. Core remains authoritative for identity, tenant, live permission, current facts, memory scope and writes. The model may propose actions; the application binds exact previews to explicit human confirmations and canonical receipts. Test all existing business and memory capabilities even where a capability is implemented as context, structured output or a UI confirmation rather than a registered model tool.

Local dummy data may be sent to the approved hosted model for these tests. Never point the test at production; keep credentials out of source/logs and identifiable real student data out of hosted tests/public evidence. Provider/model, credentials, paid usage and external rollout remain separately scoped; this policy does not execute calls or authorize deployment. Record provider/model/configuration, compatible revisions, prompts or synthetic cases, selected tools and arguments, expected vs observed results, failures, latency and usage where available, and exact focused regression commands. Preserve existing report/blog/owner review requirements.

## Runtime and execution policy (ADR 0003)

Go is the selected production AI service language; use standard-library HTTP initially. Eino is narrowly adopted for the model/tool/agent boundary after AI01 validation, with the dependency scoped to the AI service and a hard lock deferred until a separately approved adapter check. Python remains available for offline ML evaluation and research. The initial personal assistant returns one complete response through bounded synchronous HTTP using a replaceable hosted model adapter; start with a deterministic fake. Propagate cancellation and deadlines, limit concurrency, tool iterations and retries, and never keep business transactions open during inference. No token streaming, personal-task queue, local inference or heavy workflow engine in A1. Group AI later requires separate durable asynchronous processing that never blocks ordinary messaging. Preserve single-host deployment and independently scalable boundaries.

### Live model connectivity (2026-11-26)

The selected R1 live-model adapter is Eino's OpenAI-compatible component (`github.com/cloudwego/eino-ext/components/model/openai`), calling OpenAI-compatible Chat Completions endpoints directly. Configure base URL, model and API key at runtime; retain a separate deterministic fake mode. No LiteLLM proxy or extra model gateway for now; revisit only for demonstrated routing, budget or failover needs. In R1, check the component's released version against the existing Eino v0.9.23, confirm native structured tool calls and tool-result round trips with the chosen provider/model, and verify bounded execution, cancellation and errors. API compatibility is not proof of tool compatibility; do not silently fall back to fake mode. Provider/model selection, exact dependency pin, paid calls and rollout remain separately scoped. See [ADR 0003](../decisions/0003-go-bounded-requests.md).

## Documentation-driven implementation

Read official release-compatible framework documentation, examples and applicable coding skills before framework-dependent changes; verify uncertain APIs against pinned library source. Pin compatible released versions and record references, compile/build, format and run focused tests and vet; use race checks for concurrency where relevant. Review authorization, failure behavior and semantics separately from compilation. Explain the internals and trade-offs to the owner and update living evidence. No invented API, performance result or implementation acceptance. See [ADR 0003](../decisions/0003-go-bounded-requests.md). Scope, provider calls and rollout remain separately authorized.

## Planning, delegation and execution responsibilities

The architecture/review assistant is responsible for research, first-principles teaching, design alternatives, decision records, milestone briefs and reviewing supplied implementation evidence. It may edit approved planning documentation in this repository when requested. It must not write implementation or experiment code, install dependencies, configure the owner's environment, run tests/builds/benchmarks, create or trigger GitHub Actions, or perform deployment. The owner and explicitly delegated coding agents perform those tasks in the owner's development environment. Coding agents follow the approved scope and return reproducible evidence for review; the owner makes final decisions and acceptance. Discuss → learn → decide → document → delegate → review → accept. No implementation or execution is implied by a planning request.
