# A2 local retry evidence

Core `5dca3eb` and H5 `e0b2c00` add a UUID for a single visible turn.
The browser shows the pending prompt and disables sending another while
waiting. On a timeout the president can retry the same ID or edit the
prompt as a new send. A matching reply completes the existing turn.

A2 keeps no transcript outside the page. A retry may generate again
because the first reply could have been lost. There is no business write
or background retry. We considered adding a response cache, but that
would have introduced a second place holding prompts before A3's owner
and deletion model was defined.

## Checks

- Core's `python -m pytest -q tests/test_personal_assistant` passed four
  focused tests. The new test returned a timeout, retried the same UUID,
  checked the identity on the complete reply and rejected an invalid UUID.
- H5 passed `npm run type-check` and `CI=1 npm run build:h5`.
- The [A1 lab command](A1.md#reproduce) on the A2 branches intercepted the
  first browser reply as a timeout, checked the pending UI, forwarded the
  second request to Core and Go, and asserted that both requests were
  identical and only one completed turn appeared. The
  [synthetic timeout screenshot](a2-retry.png) shows the state before retry.
- An early browser run passed the retry checks and then timed out when
  the second synthetic sign-in returned HTTP 401. A1 already exercised
  the same non-president route. The rerun checked sign-in explicitly and
  passed the complete browser scenario, including non-president denial.

Owner scenario. Open Ask Campusly, simulate the timed-out request with
the browser fixture, then select **Retry**. The failed message stays visible
and the successful reply completes it once. Owner decision is pending.
Rollback uses the A1 branches. A2 adds no database migration. Cloud
measurement and real provider calls are outside this local check.
